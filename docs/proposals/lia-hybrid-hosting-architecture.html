Hybrid hosting for Lebawi International Academy

LIA physical server + LIA self-hosted cloud VM · never MaJo shared Supabase

Version 1.0 · 10 November 2026, East Africa Time (Africa/Nairobi) · Product: MaJo e-School Bridge (MayaBela)

Hard rule. LIA data must not live on the shared MaJo project hwkiihonthueadbhcvfi.supabase.co or on mayabela.pages.dev / www.majobridge.com. Both machines in this paper are LIA-owned: one in the school, one a cloud VM LIA (or MaJo on LIA’s behalf) controls.

1. What “hybrid” can mean here

MayaBela is one Flutter app talking to one API URL (SUPABASE_URL + anon key). Every desk (attendance, markbook, fees, health, bus GPS) stores rows in the same Postgres table app_documents, distinguished only by a collection name. Desks do not call each other over HTTP. They read the same collections and join in the browser (student id, class name, bus id).

So a hybrid of two machines is possible. A hybrid of two live writable databases that each own some modules is not, unless we rewrite the client. The four options below respect that.

3. Option A — Campus primary, cloud replica / public proxy (recommended)

One LIA database. The physical server is the only writer. The cloud VM is the public door (HTTPS, replica, parent phones) and a disaster-recovery copy. This is the smallest change to MayaBela: still one SUPABASE_URL. 

  Campus (LIA server room)                         Cloud VM (LIA-owned, not MaJo)
  ========================                         ==============================
  Staff PC / school Wi-Fi                          Parent phone / student / driver GPS
       |                                                |
       |  LAN or https://erp.lia....                    |  https://erp.lia....
       v                                                v
  nginx :443  (erp + api)                          nginx :443
       |                                                |
       +-- static Flutter web                           +-- same web files (or proxy)
       +-- Kong :8000  (Auth, PostgREST, Storage,       +-- WireGuard tunnel --------+
           Edge Functions)                              +-- Postgres REPLICA (read)  |
                |                                                                    |
                v                                                                    |
         Postgres PRIMARY  <----- streaming replication (WAL) -----------------------+
         (all collections)
         backups: nightly pg_dump + weekly USB

3.1 Flow — teacher takes attendance

  1. Teacher opens https://erp.lia… (LAN if on campus, public hostname if at home).
  2. Login hits school-login Edge on the campus stack (via LAN or via the cloud nginx tunnel).
  3. Auth mints JWT with app_metadata.schoolId = LIA, role = teacher.
  4. Attendance desk reads student_registry (class list) and writes attendance_sessions through PostgREST. RLS checks school + assigned class.
  5. WAL ships the new rows to the cloud replica within seconds.

3.2 Flow — parent on mobile data

  1. Parent hits the cloud hostname (campus public IP may be blocked or unstable from mobile networks).
  2. Cloud nginx sends writes (messages, link requests, FCM token) through WireGuard to campus Kong.
  3. Cloud nginx may serve reads from the replica if lag is under a few seconds; otherwise also proxy to campus.
  4. Parent JWT can only see linked children. Safeguarding collections stay denied by RLS even though they exist on the replica.

3.3 What to install

  • Campus: Ubuntu + Docker self-hosted Supabase (same stack as the LIA on-prem go-live guide) + WireGuard + nightly dump.
  • Cloud VM: Ubuntu + nginx + WireGuard + Postgres replica (or a second Docker stack with hot_standby). Same TLS names.
  • DNS: erp and api A records → cloud public IP (stable). Staff on LAN can also use a split-horizon DNS to the campus LAN IP so a WAN outage does not stop lessons.
  • Flutter web/APK: dart-define SUPABASE_URL=https://api.lia… and the LIA anon key, never the MaJo key.
Why this is first. Modules keep joining in one database. Parents get a public path. Children’s rows are not copied to MaJo. Failover is “promote the replica” — a known Postgres operation — not a second product.

4. Option B — Cloud primary, campus as cache / edge

Flip Option A. The self-hosted cloud VM holds the write database. The physical server is the school’s always-on LAN box: cached website, local replica, CCTV NVR, print, and the Flutter offline outbox if the ISP dies.

  Cloud VM (LIA)  =  Postgres PRIMARY + Auth + Edge + public HTTPS
  Campus server   =  Flutter web cache + Postgres replica + CCTV +
                     staff devices using local SQLite / CloudAppStore outbox
                     until WAN returns, then flush to cloud primary

The product already has CloudOutboxService and local stores. Staff can keep taking attendance on campus Wi-Fi during an ISP cut; queued writes upload when the tunnel is back. Parents cannot work during a cloud-VM outage (they were never on the LAN).

Pick B if Ethio/campus last-mile is worse than a proper VM in a licensed local data centre. Do not pick B if LIA’s TOR says the system of record must sit in the building.

5. Option C — Campus-only sensitive collections, cloud publish

Two LIA databases, but not two writers for the same child. Campus is the system of record. A publish worker copies only allowed collections to the cloud VM that parents hit.

  Staff desks  -->  Campus PRIMARY (all collections)
                         |
                         |  publish worker (allow-list, no medical/safeguarding/payroll)
                         v
  Parent / student / driver  -->  Cloud VM (subset replica)

5.1 Flow — publish grades

  1. Teacher writes marks on campus. They stay campus-only until academic lead approves/publishes.
  2. Publish sets a flag on grade_reports. Worker copies those rows (and the linked student display name, not the medical flag) to the cloud DB.
  3. Parent app uses a second API URL (parent build) that only knows the cloud VM.
Cost. This needs a new worker, two Flutter builds (staff vs parent), and a rule that SIS-on-cloud must not try to open health collections. Use it only if LIA legal/INSA says those collections must not be replicated off-site at all — even to an LIA VM.

6. Option D — Split modules across two live writers (do not)

Example: “academics on cloud, finance on campus”. The SIS profile, report cards, at-risk rules, and parent app all join those collections in memory. Two writers means two student ids, delayed fees, and RLS that cannot see the other school-half. We would have to invent a sync bus between modules. That is a second product.

7. End-to-end flows (Option A)

7.1 Login

  Device --HTTPS--> nginx (cloud or campus split-DNS)
                      --> Kong --> school-login (rate-limited)
                      --> bcrypt verify (schoolId+username+role)
                      --> Auth JWT (schoolId=LIA, role)
  Device stores JWT. Later calls send it. No JWT on the login page (logo is public branding).

7.2 Ordinary classroom write

  Teacher JWT --> PostgREST INSERT attendance_sessions
                    RLS: school_id = LIA AND assigned class
                    row lands on PRIMARY
                    replica receives WAL
  At-risk desk later READs attendance_sessions + grade_reports + student_registry
                    (same DB, same JWT, join in Flutter)

7.3 Privileged registry write

  Registrar JWT --> Edge school-upsert-registry
                    gate (admissions / student row)
                    service-role upsert on PRIMARY
                    student_registry row appears
  Fees, transport, markbook can now join that student id
                    — they do not wait on a second module API

7.4 Driver GPS

  Driver phone --> cloud nginx --> tunnel --> PRIMARY
                   bus_live_positions (transportId == busId)
  Parent read  --> replica or tunnel --> same collection, linked child only

7.5 WAN down at campus (Option A + split-horizon)

  Staff on school Wi-Fi --> LAN_IP nginx --> PRIMARY   (lessons continue)
  Parents on mobile     --> cloud nginx  --> tunnel X  (read replica until lag policy;
                                                        writes queue or show “campus unreachable”)
  USB / pg_dump still runs on campus

9. Recommendation

  1. Implement Option A. Campus self-hosted Supabase as primary. Cloud VM as public nginx + WireGuard + replica. One LIA Flutter build.
  2. Use split-horizon DNS so teachers on campus Wi-Fi never depend on the ISP for the API.
  3. Keep Option C in reserve only for health/safeguarding/payroll if LIA legal forbids off-site replicas of those collections — then exclude them from WAL (publication set) rather than inventing a second SIS.
  4. Do not point anything at MaJo’s shared Supabase. Do not fail over LIA onto www.majobridge.com.
