1. Purpose of this inception report

LIA's notice of intent to award asked Majo Bridge Technologies and Events PLC to attend a kick-off meeting for software requirements analysis and then to submit an inception report outlining the confirmed scope, software requirements, implementation approach, work plan, and key deliverables. This document is that report. It has five jobs:

  • Restate what LIA asked for in the Terms of Reference and confirm that our understanding is correct after the notice of award.
  • Confirm the scope: the revised list of about 49 modules, the four login portals, the customization that aligns the system with LIA's existing workflows, and the items outside scope.
  • Set out how software requirements are collected at the kick-off meeting and recorded, so every customization has a written source.
  • Describe the hybrid implementation approach: LIA's student information and sensitive data on a physical server inside the Academy, with login and other services on the Majo Bridge cloud server.
  • Lay out the week-by-week work plan, the key deliverables with their acceptance tests, the governance, the risks, and the inputs LIA must provide.

The software is already built and live. The TOR mapping in the Technical Proposal stands. This project is therefore about fitting the system to LIA: capturing LIA's workflows, configuring and customizing, standing up the two servers, loading data, training people, testing with LIA officers, and going live.

3. Our understanding of the assignment

LIA wants one Student Management System that replaces Excel grading, paper summaries, and informal messaging groups, gives every office the same student record, and keeps that record inside the Academy. The TOR success criteria (§12) are the yardstick:

TOR success criterionHow LIA will see it at go-live
Elimination of Excel-based gradingTeachers enter marks in the Weighted Markbook. Section Directors approve. Excel exists only as an export.
Real-time academic reportingDashboards, analytics, and Reports read today's marks and attendance from the school server.
Full parent engagement via portal or mobile appApproved parents see published grades, attendance, homework, and messages for their own children on web or the Android app, on campus or at home.
Improved academic performance trackingAt-risk flags (low marks + high absence), SIS history, and report cards are produced by rule from live data.
Reduced administrative workloadOne register, one approve-and-publish path, one message thread per family, one export button.

Added by LIA in the notice of award: the system must follow LIA's existing working practices, so customization is part of the scope and is driven by the requirements documented at kick-off, not by the product's defaults.

  • Portals: Administration / ERP, Teacher, Parent, and Student.

4.2 Out of scope unless agreed in the contract

  • Modules outside the revised 49-module list (finance, payroll, human resource, transport, live GPS, buses, driver portal, digital operations, campus management, CCTV). They can be added later; a change note records any such request.
  • Hardware: the LIA physical server, UPS, network equipment, backup disks, tablets, and campus cabling or Wi-Fi works. LIA procures these to the specification in Annex D; Majo Bridge installs the software on them.
  • Third-party recurring charges: SMS gateway, internet lines, domain renewals, payment gateways.
  • Re-typing of historical records on LIA's behalf. Majo Bridge provides templates, import tools, and validation; LIA offices provide and own the data.

6. Implementation approach — hybrid architecture

LIA's rule is that student information, large data, and sensitive records live on a physical server inside the Academy, while authentication and the other services run on the Majo Bridge self-hosted cloud server. The implementation uses the same system software on both machines, so LIA IT learns one tool and there is no separate middleware to buy or maintain.

School node — LIA physical server, on campus

  • Student information: identity, class, date of birth, family, admissions, alumni
  • Academic record: markbook, exam papers and attempts, report cards, attendance, at-risk flags
  • Care and conduct: health, counseling, IEP, college guidance, discipline, grievances, safeguarding
  • Large data: student documents, e-books and materials, library files, gallery photos
  • Teacher–parent messages and class discussion
  • Nightly encrypted backups on a disk LIA holds

Cloud node — Majo Bridge self-hosted cloud server

  • Authentication: School ID routing, usernames, passwords, MFA, sessions, password resets
  • Role catalogue and permissions
  • Web app delivery and Android app updates
  • Announcements, calendar, and events the school publishes
  • Push-notification delivery (the alert, not the content)
  • System health, support tools, releases

6.1 How the two servers work together

  • One login. A person signs in once at the cloud node with School ID, username or phone, and password (and MFA where required). The cloud node issues a signed session.
  • One session, two rooms. The school node is configured to trust the cloud node's signature, so the same session opens the student record on campus without a second password. Row-level security runs on both nodes: a teacher still sees assigned classes only; a parent still sees linked children only.
  • Routing by record type. The app knows the home server of every record type. Student, academic, care, document, and message records go to the school node; login, roles, published notices, and updates go to the cloud node. Nobody keeps two systems or two student ids.
  • Off campus. Parents and staff at home reach the school node through an encrypted tunnel on a school domain (for example sis.lia.edu.et). No inbound port is opened on the LIA router; the tunnel is outbound from the server.
  • On campus. Staff rooms reach the school node directly over the LAN. If the internet line fails, a teacher who signed in that morning keeps taking attendance and entering marks, because those writes land inside the campus. A fresh login during the outage waits until the line returns; parents at home wait too.
  • Why this is the simplest hybrid. Same software on both nodes, one administration console each, no custom synchronization code, and the sensitive tables never exist on the cloud node, which LIA IT can verify (UAT scenario 16).

12. Security, backups, and data protection

  • Encryption: HTTPS / TLS between the app and both nodes, and through the tunnel; disk encryption on the LIA server; encrypted backup files.
  • Access rules: row-level security on both nodes; role-based desks; safeguarding and counseling notes never in parent or student views or exports.
  • Authentication: on the cloud node with MFA (authenticator app) available; LIA decides at kick-off who must enrol from day one (recommended: Board, GM, Principal, Directors, IT Admin).
  • Audit: school audit log and grade audit log on the school node; login and role changes logged on the cloud node; both readable by leadership and QA.
  • Backups: nightly encrypted backup of the school node to a disk LIA holds, plus a weekly copy to a second disk kept off the server room; retention 30 daily and 12 weekly; restore drill before go-live and every term thereafter. The cloud node is backed up nightly by Majo Bridge; it holds no student records.
  • Key custody: LIA IT holds the server administrator account and the backup encryption key; Majo Bridge holds named maintenance accounts that appear in the audit log; the session-signing key is held by both parties under the contract.
  • Privacy desk: consent register, subject-access export, and erasure that redacts personal fields while keeping the academic record intact.
  • Project conduct: Majo Bridge staff access LIA data only for configuration, import, training, and support, through named accounts; no LIA data is used for demonstrations elsewhere; UAT uses LIA's own data under LIA's control.
